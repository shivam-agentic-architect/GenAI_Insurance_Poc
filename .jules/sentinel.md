## 2024-03-24 - Insecure File Upload and Error Leakage
**Vulnerability:** The `/api/upload` endpoint in `server.ts` uses `multer` without a file size limit, which can lead to disk exhaustion Denial of Service (DoS). Additionally, it lacks a `finally` block to guarantee temporary file deletion if an error occurs during PDF parsing or embedding generation. Furthermore, API endpoints (`/api/upload` and `/api/gpt/ask`) were returning raw `error.message` data to the client, which could leak internal stack traces or sensitive information.
**Learning:** File uploads are inherently risky and must be constrained by limits (e.g., file size). Temporary files created during the upload process must be reliably deleted using `try...finally` blocks to prevent disk space exhaustion, especially when processing steps (like PDF parsing or API calls for embeddings) can throw exceptions. Error handling must always sanitize messages sent to the client to prevent information leakage.
**Prevention:** Always configure `multer` (or similar upload middleware) with strict `limits` (e.g., `fileSize`). Use `try...finally` blocks when handling temporary files to ensure cleanup regardless of success or failure. Use generic, safe error messages in catch blocks for API endpoints exposed to the client.
