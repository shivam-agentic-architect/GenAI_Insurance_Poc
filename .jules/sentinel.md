## 2024-05-24 - [Critical File Upload Vulnerabilities and Error Leakage]
**Vulnerability:** The Express server lacked file size limits on the `/api/upload` endpoint, making it susceptible to Denial of Service (DoS) attacks via large file uploads. Additionally, if an error occurred during file parsing (e.g., corrupt PDF), the temporary file was never deleted, leading to gradual disk space exhaustion. Finally, the application leaked raw `error.message` strings in 500 responses, potentially exposing internal implementation details.
**Learning:** Default `multer` configurations are insecure without explicit `limits`. File processing must always occur within a `try...finally` block to guarantee cleanup, especially when handling user-uploaded files that might cause parsing libraries to throw exceptions. Server error responses must be sanitized to return generic messages to external clients.
**Prevention:** Always enforce strict file size limits when configuring upload middleware. Use `try...finally` blocks for deterministic cleanup of temporary resources (files, connections, streams). Implement a centralized error handling strategy or meticulously review all `.catch()` and `catch(e)` blocks to ensure they return generic HTTP 500 error messages (e.g., "Internal Server Error" or "Failed to process request") rather than raw exception details.
